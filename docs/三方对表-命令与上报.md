## 1. 下行命令（WSS：`{"type":"cmd","cmd":"...","data":...}`）

**用在哪里：** 用户在 App（或运营后台、测试台）要改灵敏度、时区、睡眠窗、触发 `play_cry` 等 → 业务服务调网关 → 网关推到设备的 **Wi‑Fi/WSS 控制面**。近场用 BLE 时，命令语义应对齐，但走 BLE 码（见「BLE 码」列），不是把本表 JSON 原样塞进 BLE。

下发入口：`POST /api/v1/device/cmd`，body `{"sn","cmd","data"}` → 网关转成设备帧。无参用 `data:{}`。

### 1.0 查询全部可下发命令（App / 管理端）

App 可先拉命令目录，再按 `example_request` 调用下发接口：

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/api/app/v1/device/commands` | App 侧 |
| `GET` | `/api/v1/device/commands` | 管理端（等价） |

成功响应：`{"code":1,"data":{total,send_method,send_path,request_body,list}}`。  
`list[]` 含 `cmd`、`data_type`、`category`、`description`、`example`、`example_request`；`play_cry` / `set_bitrate` 另含 `data_options`（可选取值对照）。

**已定样例：**

```json
{"type":"cmd","cmd":"play_cry","data":"0x65"}
```

> `play_cry` 为**服务端下发的固定叫声指令**：`data` 为 Hex 字符串（猫 `0x65`～`0x6D`，狗 `0xC9`～`0xCF`，未匹配 `0x00`）。设备播本地预置 Opus，网关不下发音频。  
> **完整情绪编号 / 文件名 / 话术对照** → **[固定叫声 play_cry 对照表](./固定叫声play_cry对照表.md)**（在线 `/#docs-play-cry`）。

**record_now 触发录音样例：**
```json
{"type":"cmd","cmd":"record_now","data":{}}
```
- 说明：约 **3s 手动录音**；设备用**固定 32kbps 独立编码器**，**不受 `set_bitrate` 影响**（回放音质优先，设计如此）。收到后开始录音，按 §6 上报 `seq=1..total` 且最后一段带 `end=1`，服务端 end=true 后触发 OSS 入库与翻译会话。

**enter_calib_ble 进入 BLE 标定样例：**
```json
{"type":"cmd","cmd":"enter_calib_ble","data":{}}
```
```json
{"sn":"...","type":"ack","cmd":"enter_calib_ble","result":0,"ts":...}
```
- 说明：`result=0` 后设备离线；App 改走 BLE——**先订阅 FFE5**，再往 **FFE4 写 `0x0D`**；FFE5 先 `CALIB:START`，约 8s 后 `CALIB:OK` 或 `CALIB:FAIL`+原因。完整时序见 [App-BLE通道协议 §4](./App-BLE通道协议.md)（在线 `/#docs-ble`）。

**仅 BLE、无对等 WSS cmd（近场/产测）：** 完整表见 [App-BLE通道协议 §1](./App-BLE通道协议.md)。

| BLE 码 | 名称 | 载荷 |
|--------|------|------|
| `0x01` | 开始配网 | `[0x01]` |
| `0x03` | 断开 WiFi | `[0x03]` |
| `0x04` | 查状态 | `[0x04]` |
| `0x05` | 查绑定 | `[0x05]` |
| `0x09` | 产测 | `[0x09, 动作]`（0 确认 / 1 拒绝 / 2 中止） |

## 2. 上行 type（WSS Text / Text+Binary）

**用在哪里：** 设备连上 WSS 之后，**固件主动上报**业务数据用的 `type` 枚举。App 通常只消费云端落库/推送后的结果，不自己发这些帧（测试台模拟硬件时除外）。

| type | Binary? | 云端处理 | 关键字段 |
|------|---------|----------|----------|
| `audio` | 是 OPUS | 入库 / Kafka / 翻译流水线 | 见 §3 |
| `retransmit` | 是 | 同音频；可精简字段，服务端回填 | `seq,crc` 最少；建议 `total,ts,codec,pid` |
| `batch` | 否（其后仍是多组 Text+Binary） | 标记批量 | `count` |
| `locate` / `geolocate` / `loc` | 否 | 透传定位；统一当 `locate` | 见 §4 |
| `notify` | 否 | 日志/透传 | `event`；如 `charging` / `bind_result` / `test_state` |
| `ack` | 否 | 日志（`result≠0` → WARN） | `cmd`,`result`（0=成功；`set_record_mode` 非法=`1`） |
| `ping` / `heartbeat`（应用层 Text JSON） | 否 | 保活 + **统一状态刷新主路径（推荐）** | 回 `{"type":"pong"}`；见 §2.1 统一状态双通道 |
| `status`（新增 2026-08） | 否 | 独立状态上报帧（备选） | 见 §2.1；只收不回 |

另：非 JSON 明文 `CHARGE:<0-100>` 若经通道到达，网关可解析为充电态（主路径仍是 BLE STAT，见 App-BLE 文档）。

### 2.1 统一状态上报：双通道（固件任选其一）

**背景**：设备长时间不录音/不上报定位时，App 查 `/api/v1/device/status` 拿到的电量/信号会是旧值。因此**强烈建议固件在 25s 心跳中顺带状态字段**（通道 A）；同时保留独立帧作为备选（通道 B）。二者刷新 Redis 快照逻辑完全一致。

| | 通道 A：`type=ping` 心跳顺带状态（**推荐**） | 通道 B：独立 `type=status` |
|---|---|---|
| **频率** | 与心跳一致，**25s** | 另设，如 60s / 发生事件时主动报 |
| **额外开销** | 几乎为 0（心跳本就要发） | 多一条包 |
| **是否回包** | 回最小 `{"type":"pong"}` | **不回包**（只收不回，省流） |
| **支持字段** | `bat / charge / rssi / bound / fw / pid / breed / db / ts` + **`motion` / `imu`** + 配置字段（全部可选） | 同 A + `event / state` + 完整 `loc_*` + `wifi_scan`；**`motion` / `imu` 同样支持** |
| **控制帧 Ping 可否** | ❌ 控制帧不带 JSON；需改成 **Text JSON** `{"type":"ping",...}` | N/A |

### 2.1.1 上报字段完整字典（双通道通用）

所有字段都**可选**；缺哪个字段就**不刷新**对应快照项（不会覆盖成 0/空，避免把上次的有效值弄丢）。  
字段名与 §3 音频上报 **100% 复用**，固件只维护一份就行。

| 字段 | 类型 | 单位/取值 | 必选 | 云端刷新到的快照字段 | 易踩坑提示 |
|---|---|---|---|---|---|
| `type` | string | `"ping"` 或 `"status"` | ✅ | — | 大小写敏感，必须小写 |
| `sn` | string | 激活时的 PT-xxx | ❌ | — | **WSS 通道可不传**（WSS 有连接级 SN 绑定），HTTP/直连才传；传了也不会错，以连接级为准 |
| `bat` | int | 0–100 | ❌ | `b` / `battery` | 超过 100 或负数会被存原值，UI 层会裁剪，别故意报超范围 |
| `charge` | **bool** | **`true` / `false`** | ❌ | `charge` | ⚠️ 是**布尔**不是 0/1！发 `0/1` 目前也被 `BoolTF` 兼容，但以后会下线兼容，固件请直接发 true/false |
| `rssi` | int | dBm，通常 -90 ~ -40 | ❌ | `rssi` | 正数也能存，UI 会当「信号很差」处理 |
| `bound` | **0 / 1** | `1`=已绑定账号 / `0`=未绑定 | ❌ | `bound` | 用数字 0/1；`Bool01` 同时兼容 true/false，但按表走数字 |
| `fw` / `fw_ver` | string | `"2.0.0"` 等 | ❌ | `fw_ver` | 两个键名都认，哪个非空取哪个；只推荐用 `fw`（跟下行 ack 对齐） |
| `pid` | string | App 宠物档案 ID，**未绑定用 `""`** | ❌ | `pid` | ⚠️ **强制纯数字整型串**（例 `"123"`），不允许字母/前缀/符号；旧 uint32 `4294967295` 或 `"FFFFFFFF"` 视为未绑定兼容 |
| `breed` | string | 品种字符串 `"dog"` / `"cat"` / `"other"` | ❌ | `breed` | ⚠️ **字符串！不再用品种编码 0/1**；云端原样存，前端字典会翻译成中文名/图标；自定义品种直接传字符串即可 |
| `db` | number | 声压 dBFS（*1000 传整数也行） | ❌ | `db` | 空闲态典型值 -1200 ~ -600；叫起来会到 -100 以上 |
| `ts` | int64 | **Unix 微秒 μs**（绝对） | ❌ | `last_seen_at` / 排序键 | ⚠️ **微秒！** 不是毫秒。17 位左右。秒数 * 1_000_000 再填 |
| `motion` | string | `walk`/`run`/`stand`/`prone`/`lie`（走/跑/站/趴/躺） | ❌ | `motion` / `motion_label` | **ping 与 status 都建议带**；姿态变化时立刻用 status 刷新。枚举说明见 [设备状态 §2.3](./设备状态与配置上报.md) |
| `tier` | string | `normal`/`light`/`deep`（正常/浅睡/深睡） | ❌ | `tier` / `tier_label`；`in_sleep` | **档位变化立刻 status**；ping 顺带；light/deep → `in_sleep=true` |
| `imu` | array | `[{ts,acc,gyro}]`；acc=g，gyro=dps | ❌ | `imu`（快照最近一次） | **ping 可带最近 1～数点**；录音仍以音频帧 `imu` 为主；status 可在姿态变化时附带 |
| —— 以下仅通道 B 推荐带（ping 通道也能解析到，但一般不建议心跳带，浪费包长） —— |
| `event` | string | 见 §2.2 事件枚举（`audio_start`/`audio_end`/`idle`/`play_start`…） | ❌ | `last_event` | 事件触发时建议立刻发一帧 `type=status + event`，比等下一轮心跳更及时 |
| `state` | string | 见 §2.2 状态枚举（`recording`/`playing`/`idle`…） | ❌ | `last_state` | 状态变化时主动发，不要等心跳 |
| `loc_lat` / `loc_lng` | float64 | WGS-84 经纬度（GPS/融合解算后） | ❌ | `last_loc_lat` / `last_loc_lng` | 0 / 0 视为「未知」，不会覆盖旧有效坐标 |
| `loc_acc` | float64 | 米 | ❌ | `last_loc_acc` | GPS 典型 5~20；WiFi 典型 30~100 |
| `loc_ts` | int64 | **Unix 微秒** | ❌ | `last_loc_ts` | 同 `ts`，微秒 |
| `loc_speed` | float64 | m/s | ❌ | — | 保留，暂不落 UI |
| `wifi_scan` | array\<object\> | 见 2.1.4 wifi_scan 结构 | ❌ | 存到定位指纹缓存 + 反查坐标 | 一般只有 HTTP 定位时会带；WSS `status` 通道仅在无法发 HTTP 时当兜底 |

| `volume` | int | **0~100** | ❌ | `volume` | 与 `set_volume` 一致；建议 ping/status 周期或变更时带 |
| `sensitivity` | int | **0~100** | ❌ | `sensitivity` | 与 `set_sensitivity` 一致 |
| `translate_enabled` | **0/1** | 自动录音开关（旧名） | ❌ | `translate_enabled` / `auto_record` | 兼容旧固件；与 `auto_record` 同义 |
| **`auto_record`** | **0/1** | **自动录音开关**（推荐） | ❌ | `auto_record` / `translate_enabled` | **1=开 / 0=关**；默认 0；关时网关丢弃上行录音；见 **§2.1.1a** |
| `sleep_enabled` | **0/1** | 夜间休眠总开关 | ❌ | `sleep_enabled` | 与 `enable_sleep` 一致 |
| `sleep_window` | string | **`"0:6"`**（开始:结束 小时） | ❌ | `sleep_window` | 与 `set_sleep_window` 一致 |
| `loc_interval_ms` | int | 毫秒，如 `30000` | ❌ | `loc_interval_ms` | 与 `set_loc_interval` 一致 |
| `proto_ver` | int | 协议版本 | ❌ | `proto_ver` | 可选 |
| `ch` | int | WiFi 信道 | ❌ | `ch` | 可选 |

> **配置双通道**：设备上行带配置字段 → `config_source=device`；App 下行 cmd 后未回显 → `config_source=shadow`。详见 [设备状态与配置上报](./设备状态与配置上报.md)。

> **`bound`（App 查询）**：设备 JSON 可继续上报 `bound`（兼容旧固件），但 **App 状态接口的 `bound` 由网关按 `pid`+`breed` 计算**，不以设备 `bound` 为准。

#### 2.1.1a `auto_record` 上报与网关处理

| 环节 | 约定 |
|------|------|
| 设备默认 | `auto_record=0`（关） |
| App 状态默认 | `/device/status` 的 `auto_record` 未确认前为 **`false`** |
| 下行 | `enable_auto_record`，`data`=`"true"`/`"false"`（兼容 `1`/`0`）；旧名 `enable_translate` |
| ACK | `{"type":"ack","cmd":"enable_auto_record","result":0}`；**仅成功 ACK 后**网关才改状态 |
| 上行 | `ping`/`status` 带 `"auto_record":0\|1`（推荐）；旧字段 `translate_enabled` 兼容并同步 |
| 优先级 | 设备上报 **覆盖** ACK 写入值 |
| 录音分流 | 只按 `kind`：`0` 事件流 / `1` 录音文件；无 `kind` 默认事件流。两路分桶；默认翻译事件流、文件可归档（`audio.*`） |

```text
默认 false（丢录音）→ 下发 true → ACK result=0 → 状态 true（收录音）
→ ping/status 回显 auto_record:1（以上报为准）→ 再关则继续丢录音
```

在线完整说明：**设备状态与配置** `/#docs-device-status` §2.1.1；嵌入式 `/#docs` §6.6.1。

### 2.1.2 通道 A 完整示例（推荐：25s 心跳 `type=ping` 顺带状态）

**复制粘贴，改数值直接发**。所有字段可按需删减，**`type=ping` 必须留**；心跳应答仍是最小 `{"type":"pong"}`。

```json
  "charge": false,
  "rssi": -55,
  "bound": 1,

  "breed": "dog",
  "db": -625,

```

👉 未绑定宠物时，**`pid` 填空字符串**（App 侧 `bound` 由网关按 pid+breed 计算为 0）：
```json

```

👉 最精简版（完全没实现字段的裸板先跑通链路，后接真实传感器）：
```json
{ "type":"ping" }
```

👉 **🔧 【推荐全量版】25s 心跳通道 A（把所有能报的都带上，App 状态页就不会有空字段）**：  
把 Checklist 里前 9 项（bat/charge/rssi/bound/fw/pid/breed/db/ts）全填上，App 设备卡片的电量/品种/固件/声压每 25s 就能拿到一次，不需要等其他事件触发上报。

```json
{
  "type": "ping",
  "bat": 78,
  "charge": false,
  "rssi": -55,
  "fw": "2.0.0",
  "proto_ver": 1,
  "pid": "123",
  "breed": "dog",
  "db": -625,
  "ts": 1756210523456789,
  "volume": 65,
  "sensitivity": 80,
  "auto_record": 1,
  "translate_enabled": 1,
  "sleep_enabled": 1,
  "sleep_window": "0:6",
  "loc_interval_ms": 30000,
  "motion": "walk",
  "imu": [
    {"ts": 1756210523456789, "acc": [0.01, 0.0, 1.0], "gyro": [0.5, -0.2, 0.1]}
  ]
}
```

| 字段 | 为什么心跳也要带 |
|---|---|
| `fw` | App「关于设备」页要显示固件版本，如果只在激活时发，用户升级后没复位或没重新激活就会一直显示老版本号 |
| `breed` | App 首页卡片要显示品种（"dog"/"cat"/"other" 或自定义品种名），只在事件/定位上报时带的话，空闲 30min 可能显示空或老品种 |
| `db` | App 实时声压条（dBFS 进度条），每次心跳带最新值用户能看到"咪头有没有采到声" |

| `ts` | 心跳的设备侧时间，用来校准设备 RTC（跟网关时间差多少），也防止重放/乱序包 |
| `motion` | App 实时显示走/跑/站/趴/躺；空闲不录音时也要靠心跳刷新 |
| `imu` | 心跳带**最近 1～数点**即可（不必 50Hz 狂发）；录音对齐仍以音频帧 `imu` 为主 |


- **补齐后的全量版（复制粘贴发这条就好，每个字段都用上了）**：
```json
{
  "type": "status",
  "bat": 78,
  "charge": true,
  "rssi": -62,
  "bound": 1,
  "fw": "2.0.0",

  "breed": "dog",
  "db": -625,
  "event": "idle",
  "state": "idle",
  "loc_lat": 31.23,
  "loc_lng": 121.47,
  "loc_acc": 50,
  "loc_speed": 0,
  "loc_ts": 1720000000000000,
  "ts": 1756210523456789
}
```

**精简版 → 全量版，这次多补了 5 个字段的意义：**

| 多补的字段 | 为什么强烈建议通道 B 也要带 |
|---|---|
| `fw` | 用户升级完固件，事件/状态变化时立刻带 fw，App 关于页不用等下一轮心跳就能看到新版本号 |
| `breed` | 用户在 App 改了宠物品种（"英短→布偶"），设备端 breed 缓存同步后，事件/状态变化时立刻带上，首页卡片 1~2s 内就切换新品种图标，不用等 25s 心跳 |
| `db` | 触发事件（比如 audio_end 录音结束）时带当前的声压 dBFS，App 详情页里就能显示这条录音是"很大的狗叫/很小的哼唧" |
| `state` | 只有 `event=idle` 没有 `state=idle` 时，App「设备当前状态」卡片只能显示事件名，没法区分"正在录音/正在播放/空闲 3 态"；建议 `event + state` 两个字段**永远一起带**（event=发生了啥，state=现在停留在哪种状态） |
| `ts` | `loc_ts` 只是定位的时间，`ts` 是整个上报包的设备侧时间；**两个都填**，否则网关用服务器当前时间写 `last_seen_at`，如果网关延迟/排队 1s，last_seen_at 和真正的上报时刻就对不上 |

> 💡 包长影响？全量版（两个数组字段 wifi_scan/loc_macs 都空的话）大概 280~320 字节；加上 `wifi_scan` 3~5 个点大概 450~600 字节，在 MTU 1400 以上的 WSS 通道里**都是单包就能发完**，不会分片，对嵌入式内存压力可以忽略。

### 2.1.4 `wifi_scan` 单个 AP 的结构（HTTP/WSS 通用）

`wifi_scan` 是数组，每个元素字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `mac` | string | ✅ | 路由器 BSSID，冒号分隔小写/大写都认（`aa:bb:cc:dd:ee:ff`）；兼容 `-` 分隔 |

### 2.1.6 最常见的 5 个协议坑（嵌入式提测前自查一下，能省 80% 联调时间）

| # | 坑 | 正确写法 | 触发现象 |
|---|---|---|---|
| 1 | `charge` 发了 `0/1` | 直接发 true/false | 目前 `BoolTF` 兼容 0/1，但「0」是 falsy，逻辑对；**不建议长期依赖兼容** |
| 2 | `ts` / `loc_ts` 传了毫秒（13 位） | 微秒，17 位：`秒 * 1_000_000` | 音频段首绝对时间排序错乱 + 段首强制识别（>500ms 判定）误判 |
| 3 | `pid` 未绑定时传了 `4294967295`（uint32 max） | 直接传 `""` 字符串 | 兼容层会把这个数字当成「未绑定」，但 App 侧可能还会把 pid 原样显示，很怪 |
| 4 | `bound` 传了 `true/false` | 按表传 `0/1` 数字 | 现在 `Bool01` 兼容 bool，但以后会下线兼容 |
| 5 | 通道 B 丢包后靠「上一轮心跳 60s 周期」刷新 | 关键 event/state 变化时**立刻单独发一帧 status** | App 会看到「录音都结束 50s 了卡片上还显示 🎙️ 录音中」 |

## 2.2 `event` / `state` 枚举（运行态）

**用在哪里：** `type=status`（通道 B，**推荐**）或 `type=notify` 的 JSON 里。网关原样写入 `last_event` / `last_state`，**不校验枚举**（未知字符串也会存）；App 通过 `GET /api/v1/device/status` 查询。

### 2.2.1 `state` 与 `event` 的区别

| 字段 | 语义 | 刷新到的 API 字段 |
|------|------|-------------------|
| `state` | **当前停留在哪种运行态**（持续） | `last_state` |
| `event` | **刚发生了什么**（瞬时事件，可选与 state 同值） | `last_event` |

**强烈建议 `event` + `state` 成对上报**（尤其在 `type=status` 里）：

- `event` = 触发了什么（如 `audio_end`）
- `state` = 现在停在哪（如 `idle`）

只发 `event=idle` 不发 `state=idle` 时，App 无法区分「正在录音 / 正在播放 / 空闲」。

### 2.2.2 `state` 推荐枚举

| `state` | 含义 | App `state_label` | App `in_sleep` | 典型上报时机 |
|---------|------|-------------------|----------------|--------------|
| `idle` | 空闲 | 空闲 | false | 默认态；录音/播放结束后 |
| `recording` | 录音中 | 录音中 | false | 开始采音、上行 `type=audio` 期间 |
| `playing` | 播放 TTS / 叫声 | 播放中 | false | 收到下行 `tts` / `play_cry` 正在播 |
| `locating` | 定位中 | 定位中 | false | GPS / WiFi 定位进行中 |
| `ota` | OTA 升级中 | 升级中 | false | 固件升级过程 |
| `sleep` | 夜间休眠 | **睡眠** | **true** | 进入休眠时段（见下） |
| `sleeping` | 夜间休眠（`sleep` 别名） | **睡眠** | **true** | 同上 |

网关还把以下值视为休眠（`in_sleep=true`，`state_label=睡眠`）：`night_sleep`、`deep_sleep`（大小写不敏感）。

**夜间休眠进入条件（固件）：** 需先收到 `enable_sleep=1`，再按 `sleep_window`（如 `"8:10"` / `"0:6"`）在**整点**判断当前小时是否在窗口内；在则进睡眠并上报 `state:"sleep"`（建议 `event:"sleep_enter"`）。关 `enable_sleep` 或离开窗口后报 `state:"idle"`。细节见 [设备状态与配置上报 §2.2](./设备状态与配置上报.md)。

| 值 | 说明 |
|----|------|
| `awake` | 旧文档示例中的「非休眠」；**新固件建议统一用 `idle`** |
| 其它字符串 | 可存，但 App 可能无对应 UI，联调前与 App 对齐 |

### 2.2.3 `event` 推荐枚举

| `event` | 含义 | 建议配对 `state` |
|---------|------|------------------|
| `audio_start` | 开始录音 | `recording` |
| `audio_end` | 录音结束 | `idle` |
| `play_start` | 开始播放 TTS/叫声 | `playing` |
| `play_end` | 播放结束 | `idle` |
| `idle` | 回到空闲（可与 state 同值） | `idle` |
| `locate` | 进入定位 | `locating` |
| `locate_update` | 定位结果更新 | `locating` 或 `idle` |
| `sleep_enter` | 进入夜间休眠 | `sleep` / `sleeping` |
| `sleep_exit` | 退出夜间休眠 | `idle` |
| `ota_start` | 开始 OTA | `ota` |
| `ota_end` | OTA 结束 | `idle` |
| `motion_change` | 运动姿态变化 | 保持当前运行态；另带 `motion` 字段 |
| `tier_change` | 功耗档位变化 | 保持当前运行态；另带 `tier` 字段 |

### 2.2.3a 运动姿态 `motion`（走 / 跑 / 站 / 趴 / 躺）

与 `state`（运行态）正交。字段名 **`motion`**，写入状态快照，App 返回 `motion` + `motion_label`。完整上报时机与示例见 [设备状态与配置上报 §2.3](./设备状态与配置上报.md)，此处只保留对表枚举。

| `motion` | 中文 | 说明 |
|----------|------|------|
| `walk` | 走 | 步行 |
| `run` | 跑 | 奔跑 |
| `stand` | 站 | 站立 |
| `prone` | 趴 | 趴卧 |
| `lie` | 躺 | 侧躺/仰躺 |

兼容中文 `走`/`跑`/`站`/`站立`/`趴`/`躺`。`type=ping`、`type=status`、音频元数据都可带。

### 2.2.3b 功耗档位 `tier`（正常 / 浅睡 / 深睡）

与 `state`、`motion` 正交。字段名 **`tier`**，写入状态快照；App 返回 `tier` + `tier_label`；`light`/`deep` 时 `in_sleep=true`。

| `tier` | 中文 | 说明 |
|--------|------|------|
| `normal` | 正常 | 正常工作态 |
| `light` | 浅睡 | 静音 ≥5min 触发；有网保 WiFi / 无网关射频保 BLE |
| `deep` | 深睡 | 浅睡后再静音约 5min；充电/配网态阻断 |

**推荐：** 档位变化立刻 `type=status` + `event=tier_change` + `tier`；`ping` 顺带当前档位。

```json
{"type":"status","event":"tier_change","tier":"light","bat":78,"ts":1756210523456789}
{"type":"ping","tier":"normal","bat":78,"ts":1756210523456789}
```

### 2.2.4 `type=notify` 常用 `event`（非 status 帧）

`notify` 也可带 `event` / `state`，主要写日志并刷新快照，**不回包**：

| `event` | 说明 |
|---------|------|
| `charging` | 充电状态变化 |
| `bind_result` | 绑定/解绑结果 |
| `test_state` | 产测（如 `state=loop`） |
| `connected` | 服务端下发，提示设备已上线 |
| `token_expired` | 服务端下发，提示 token 过期 |

## 5.1 业务 / 管理 HTTP（云端路径，新增 2026-08）

**用在哪里：** App 后端、运营后台、测试台查设备实时状态；与 `§1` 下行命令同层入口（`/api/v1/device/...`），不经过设备 SN+Token 鉴权。

| 方法 | 路径 | 用途 | 鉴权 |
|------|------|------|------|
| GET/POST | `/api/v1/device/status` | **查单台设备完整状态快照**（见下表字段） | 内网开放，与 cmd/tts 同级别 |
| GET/POST | `/api/v1/device/status/list` | **批量查**（支持 SN 列表、仅在线过滤、默认返回全部本地在线设备） | 同上 |
| POST | `/api/v1/device/cmd` | 下行命令（见 §1）；**设备离线自动入队，上线后下发**（见 §5.1.0） | 同上 |
| POST | `/api/v1/device/tts` | 下行 TTS（见 §1）；TTS **不入队**，离线直接失败（与 cmd 区别） | 同上 |

### 5.1.0 下行命令的离线入队语义（重要）

**`/api/v1/device/cmd`（只针对 cmd）** 有「保险起见不丢命令」的语义：调用时只要请求格式合法、Redis 可达，接口 HTTP 统一返回 **200**，但响应里会告诉你走的是哪条分支：

| 字段 | 类型 | 在线（`online=true`） | 离线 / 通道关闭 / SendCh 写超时 |
|------|------|------|------|
| `delivered` | bool | `true` | `false` |
| `queued` | bool | `false` | `true` |
| `status` | string | `"delivered"` | `"queued"`（便利字段，直接取来判断） |
| `queue_len` | int | 当前离线队列长度（一般 0） | 当前队列长度（含本条，通常 ≥1） |
| `note` | string | `"delivered to conn sendch"` | `"device offline, queued"` 或 `"conn closed, fallback queued"` 或 `"sendch write timeout, fallback queued"` |

**在线场景示例响应：**
```json
{
  "code": 1,
  "data": {
    "cmd": "reboot",
    "type": "cmd",
    "delivered": true,
    "queued": false,
    "status": "delivered",
    "queue_len": 0,
    "note": "delivered to conn sendch"
  }
}
```

**离线场景示例响应：**（设备未连接 / 心跳已过期 → 命令写入 `pet:offline_cmd:{SN}` Redis List）
```json
{
  "code": 1,
  "data": {
    "cmd": "set_sensitivity",
    "type": "cmd",
    "delivered": false,
    "queued": true,
    "status": "queued",
    "queue_len": 1,
    "note": "device offline, queued"
  }
}
```

**设备上线时的下发时机：** 设备完成 WebSocket 握手成功后 → 先推送 `{"type":"notify","event":"connected"}` → 立刻 `flushOfflineCmds` 按入队顺序依次下发全部离线命令 → 下发成功后清空 Redis List。中途若通道再次关闭/写超时，未下发完的条目会**再次回存入队**（反向 LPUSH，保持顺序），不会丢。

**对比 TTS：** `/api/v1/device/tts` 仍是「设备离线 → 立即 HTTP 500 返回错误」不入队（与现有行为一致），因为 TTS 含实时音频数据，长时缓存意义不大。

### 5.1.4 实现与 Redis Key（对下游透明，仅运维/排错参考）

网关把实时状态聚合落到一个统一 JSON key，查询时再实时合并其它 key 取最新值：

| Redis Key（加 `redis.key_prefix` 前缀） | 类型 | 说明 |
|------|------|------|
| `pet:device:status:{SN}` | JSON string | **统一状态主 key**，`UpdateDeviceStatus` 增量写；`TTL=0`（永久，保留历史） |
| `pet:online:{SN}` | string `"1"` | 在线标记，TTL=`redis.online_ttl`（90s）；心跳刷新 |
| `pet:conn:{SN}` | string | 当前 connID，TTL=90s |
| `pet:device:meta:{SN}` | JSON string | activate 写入的 SN/FW/MAC/激活时间 |
| `pet:device:last_loc:{SN}` | JSON string | 最近一次 WiFi 指纹解析后的坐标（另一条路径写入） |

`GET /api/v1/device/status` 的 `GetDeviceStatus` 内部是**一次 Redis TxPipeline** 把上面 5 个 key 全部读出并合并，保证 `online` 是心跳级实时、其余字段是最近一次上报的快照。

## 6. 错误码 / 回执（云端已有）

**用在哪里：** 设备处理 HTTP 失败与命令 `ack`；App/固件对表时确认「哪些 code 已有约定、哪些业务码还没定」。

### 6.1 HTTP

| code | 含义 | 固件建议 |
|------|------|----------|
| `0` | 成功 | |
| `401` | token 无效/过期 | refresh 后重连 |
| `429` | 过频 | 退避 |
| `4xx` | 参数/业务 | 看 `msg`，勿死循环 |
| `5xx` | 服务端 | 退避重试 |

### 6.2 WSS ack

```json
{"sn":"...","type":"ack","cmd":"enable_auto_record","result":0,"ts":...}
{"sn":"...","type":"ack","cmd":"enable_translate","result":0,"ts":...}
{"sn":"...","type":"ack","cmd":"set_record_mode","result":0,"ts":...}
{"sn":"...","type":"ack","cmd":"set_record_mode","result":1,"ts":...}
{"sn":"...","type":"ack","cmd":"play_cry","result":0,"ts":...}
{"sn":"...","type":"ack","cmd":"enter_calib_ble","result":0,"ts":...}
```

| result | 含义（云端约定） |
|--------|------------------|
| `0` | 收到并执行成功 |
| `1` | 参数非法等业务错误（已确认：`set_record_mode` 非法值回 `1`，串口 `[CMD] Invalid record mode`） |
| 其它非 0 | **错误码表待三方继续补**（云端目前记日志：`result≠0` 打 WARN） |

**已确认会回 ack 的 cmd：** `enable_auto_record` / `enable_translate`、`set_record_mode`、`enter_calib_ble`（`result=0` 后设备离线进 BLE 标定）；其它命令仍建议逐步补齐。  
网关侧：收到 `type=ack` 记日志（失败升 WARN）。对 **`enable_auto_record` / `enable_translate`**：成功 ACK（`result=0`）后把下发期望值写入状态快照 `auto_record`（默认本为 `false`）；之后设备 `ping`/`status` 上报覆盖。关着时上行录音会被丢弃。详见 **§2.1.1a**。HTTP 下发 `status=delivered` 只表示「已进下行通道」。

### 6.3 连接层（非 JSON code）

| 现象 | 含义 |
|------|------|
| HTTP 403 Upgrade | SN/token 握手失败 |
| 主动断开 | 心跳超时等；**上行超限不再踢线**（告警放行；音频 Text+Binary 算 1 次 QPS） |
