【网关现行规则 · 2026-09】
设备帧已带 kind：{"type":"audio", ..., "retransmit":0, "crc":..., "kind":0|1}
  kind:0 = 事件流（叫声实时流，边采边传）
  kind:1 = 录音文件（本地录完再拆帧上传；seq=0 开段、end=1 收段为完整文件）

事件流帧长（联调定稿 · 2026-09-15：60ms 包 @ 16k PCM）：
  - kind=0/1 **采集同源 16kHz**（AUDIO_SAMPLE_RATE=16000）；差异仅码率与每包采样数
  - 事件流：麦克风仍按 20ms 读，**攒 3×20ms PCM 后一次 opus_encode → 1 个 60ms Opus 包**
    （1 Binary = 1 Opus 包，不是 3 个 Opus 帧）；相对 ts 步进 **60000µs**
  - 录音文件：1×20ms PCM → 1 个 20ms Opus 包；相对 ts 步进 **20000µs**
  - Opus 解码固定 48k；Ogg InputSampleRate 只是元数据，两路均标 **16000**
  - 网关：按 seq 连续拼装，granule 按 TOC **包总时长**累加；缺 seq 补洞间隔
    kind=0→60ms、kind=1→20ms；MP3 经 aresample（默认 44100）；不认收包墙钟
  - 码率：`set_bitrate` `"0"/"1"/"2"` = 16/24/32 kbps（只影响本事件流）；**码率≠音量**
  - **不插包间静音**（pace_align 默认关）；**不做听感后处理/自动 atempo**（默认全关）
  - 验收：missing=0 且 toc_ms ≈ chunk_ts 跨度，median_gap≈60；听感应连续、音调正常

录音文件帧长（kind=1：20ms/包 @ 同源 16k）：
  - SPIFFS `/rec_n.opus`：`[u16-LE len][opus]×N`；约 3s；上传 seq 从 0，`ts=base+seq×20000`，末帧 end=1
  - 约 32kbps；断线 retransmit=1 补发（绝对 ts）
  - 网关：分桶；缺 seq 插零长度洞（granule/ts 按 **20ms**）；Ogg InputSampleRate=**16000**；total 滚动值以 end + MaxSeq+1 为准
  - 变尖变快：查 MP3 是否误把 48k PCM 按非 16k 声明；不是「文件是 32k 采集」

服务端：
1. 只按 kind 分桶；无 kind 默认事件流(0)。不再用 db==-600（事件流静音帧 db 可到 -1000，会误分桶）
2. 两路各自按 seq/end 分段，补发（retransmit=1）并回同 kind 原段，绝不混拼
3. 配置 audio.accept / audio.translate / audio.archive_other
   推荐默认：accept=both（两路都存）、translate=event（只翻事件流）、archive_other=true（文件路只 OSS 归档）
4. kind:1 收到 end=1 即整段完整可入库；kind:0 同样按段拼包再解码
5. 每帧 CRC32 校验不过 → 当丢帧，不拼进文件
6. end 后用 end 帧 total（或 MaxSeq+1）与去重入库帧数对比；迟到补发若段已转码，重拼覆盖 OSS 原对象
7. 拼接时间轴：只认设备 ts（chunk_ts）与 seq；**禁止用网关 received_at 当音频时间**

两种区分方法的原理（举例说明）
两条路径的帧长得一样（都是 "type":"audio"），差别在字段值和前后事件帧：
1：事件流（叫声实时流）：
{"type":"status","event":"audio_start"}        ← 叫声确认时发
{"type":"audio","db":-45,...,"kind":0}         ← db=真实测得分贝×10，每帧不同
{"type":"audio","db":-38,...,"kind":0}
{"type":"status","event":"audio_end"}          ← 叫声结束时发


2：录音文件上传（record_now，手动或自动触发）：
{"type":"status","event":"audio_start"}        ← 录音开始前发一次
（设备嘀一声，本地录 ~N 秒到 /rec_N.opus）
{"type":"audio","db":-600,...,"kind":1}        ← 全部帧固定 -600（=-60.0dB×10）
{"type":"audio","db":-600,...,"kind":1}        ← 一批连发，没有 audio_end
{"type":"ack","cmd":"record_now","result":0}   ← 以 ack 收尾



服务端区分：

1：主判据：kind（0 事件 / 1 文件）；无 kind 默认事件流。不再用 db 分流。

2：交叉校验：audio_start→audio_end 成对包住的是事件流；一批录音帧后面跟着 record_now ack、没有 audio_end 的是录音。



两条路径各自都是完整独立的音频，同一次叫声本来就会收到两份



两份数据不要拼一起，内容本来就是重复的，拼了反而会坏。
区分方法是这样的，收到 audio 帧先按 kind（或旧 db）分两组。录音文件一组，事件流一组。事件流这组有 audio_start 和 audio_end 一对事件帧包着，中间的帧拼起来就是一次完整叫声。录音那组没有 audio_end，别等它，这组自己有边界，seq 从 0 开始，到 end 等于 1 结束，最后还会跟一条 record_now 的 ack，按这个收尾就行。
有个地方要注意，两条路径都会发 audio_start，所以一定要先分组再去拼段，不然录音那批帧会混进事件流里，两段数据都会都拼坏。

时长上，事件流是叫声有多长就传多长，最短 800 毫秒，因为不足 800 毫秒的短声固件直接丢弃不上传。录音是固定 3 秒左右，开头 800 毫秒是从叫声起点截的前导，后面补录凑满 3 秒。

关于每次来两份的问题，这两份大部分是同一段声音，所以合并没有意义。如果你们那边不需要存档回放功能，最简单的处理是给我发 enable_auto_record 0 把自动录音关掉，之后每次叫声就只有事件流一份，协议什么都不用改。App 上手动点录音的 record_now 不受影响，还是会有录音文件。如果想保留存档，那就维持现状，你们按上面说的分两组，事件流喂识别引擎，录音单独归档，互不拼接就行。



主判据，看 kind 字段（旧固件看 db）
kind=1 或 db 等于负 600：录音文件上传
kind=0 或 db 大于负 600：事件流（叫声实时流，每帧是真实测得分贝乘 10）



辅助判据
事件流：audio_start 和 audio_end 成对出现，帧带 imu 数组，帧间 db 值各不相同
录音上传：没有 audio_end，一批帧 seq 从 0 到 end 等于 1 自己成段，后面跟 record_now 的 ack，帧不带 imu
断网补发的帧 retransmit 等于 1，分桶规则不变（补发录音帧还是 kind=1，补发事件帧还是 kind=0）


服务端处理逻辑
1：收到 type 是 audio 的帧，先按 kind 分到两个桶
2：每个桶内部按 seq 等于 0 开新段、end 等于 1 收段，各自独立拼接，两条桶的帧绝不混拼；补发按 seq+时间戳并回原段
3：默认事件流桶喂识别引擎，录音桶做归档回放（可用 audio.translate / archive_other 调整）

事件流组装补充约定（设备侧 · kind=0）
1：语义上按 audio_start / audio_end 成对切一段；段内中间停顿不用管。网关落库切段用同源边界 seq=0…end=1（与 start/end 事件成对），status 事件只打点不单独切文件。
2：同一段内 seq 应连续；断号/重复按 sn+kind+段锚+seq+total(+crc) 去重（相对 ts 先折绝对，勿把相对/绝对 ts 混进指纹），首传断号打 warn，补发并回原段。
3：段尾约 500ms 静音窗口也在流里（干净静音帧），组装后听到「结尾一小段安静」是预期，不做裁剪。
4：帧长口径（定稿 60ms）：事件流 **60ms 连续边采边传**（3×20ms PCM→1 Opus 包，TOC=60ms，ts 步进约 60000µs）。网关按 Opus TOC 连续拼装，不插 PLC 包间静音；缺 seq 洞按 60ms 计。诊断：toc_ms / span_ms / median_gap_ms / wall 应接近（median_gap≈60）。码率 16/24/32kbps 只影响清晰度，不改变音量与音调。


是的，两个桶装的就是同一次叫声的声音，内容基本重复，这一点你理解得没问题。区别只是包装方式不一样。


事件流实时传延迟低，录音要等录完再传慢好几秒。另外事件流的帧还带真实分贝和 IMU 动作数据，录音帧这些都没有，识别引擎能用的信息更全。


enable_auto_record 是现有命令，当前固件就支持，发一条 enable_auto_record 0 就生效，而且这个开关写进了 NVS，设备重启后也是关的状态，发一次就行。改完可以看 ping 或者 status 帧里的 auto_record 字段，变成 0 就是关掉了，之后每次叫声就只有事件流一份音频。











首先说明一点：这两路音频的声源是同一个，都是设备固件通过麦克风实时采集的原始声音，不是服务端合成或App录的。区别在于固件怎么处理、以什么形式传给你们。

事件流（kind=0）是实时翻译链路的产物。固件翻译任务一直在监听麦克风，检测到叫声并确认是有效声音后（超过800ms的短段过滤门槛），会先发一条 audio_start 事件，然后把叫声期间的声音按约定帧长（定稿 60ms）做完降噪和 OPUS 编码后逐帧实时推上来，叫声结束后再发 audio_end。也就是说，你们收到的事件流不是现成的文件，而是散的帧序列，需要你们按 seq、total、ts 这些字段在服务端按时间顺序组装成一个完整文件，组装出来的才是“事件流录音文件”。

自动录音（kind=1）是固件本地录好的完整文件。叫声确认后，固件会在设备本地录一段3秒的音频（其中包含叫声之前1秒的前导内容，所以开头不会缺），录完存到本地，再作为一个完整的录音文件按 **20ms/包、同源 16kHz PCM、约 32kbps** 分帧上传给你们。它和事件流的区别就是：事件流是边录边传、你们拼装；自动录音是固件先录完再传、收到就基本是成品。另外自动录音有30秒节流，同一次叫声确认后30秒内不会重复触发，这是设计行为不是bug。

关于你们怎么处理这两路音频，有几点请注意：

第一，用 kind 字段分桶。kind=0 归到事件流，kind=1 归到录音文件，两条链路建议分开存储和展示，不要混在一起。

第二，去重口径：相对 ts 先折绝对，再按 sn + kind + 段锚 + seq + total(+crc)。因为设备断线重连后会有补传机制，可能出现 retransmit=1 的帧，和之前实时首传的内容重复，按这个口径去重即可。特别提醒：即使翻译和自动录音两个开关都关着，重连后仍可能出现 kind=1 且 retransmit=1 的历史录音补发帧，这是正常的，不要当成异常上报。网关会把补发帧并回同 kind 原段（按库内 device_ts / 未收尾段 / 时间窗找回），不要当成新段。

第三，注意开关组合的行为边界。翻译开、自动录音关：只有 kind=0 事件流；两个都开：事件流之外还会有 kind=1 录音；翻译关、自动录音开：设备不会有任何音频上行，因为叫声检测逻辑目前位于翻译任务内部，翻译关了检测也就停了，这是固件现状。手动 record_now 命令不受翻译开关影响，随时可用。
