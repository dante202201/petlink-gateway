模块功能与测试进度总结
（整理时间：2026-08-03）

把目前 PetTranslator 程序里的模块和测试情况梳理了一遍，写下来方便后面接着干。

一、程序里都有哪些模块，分别干什么

整个固件跑在 ESP32-S3 上，主入口是 PetTranslator.ino，其余都是按功能拆出来的模块。文档里说一共 17 个模块，就是 common.h 加 15 个功能模块再加主文件。

一个一个说：

common.h
全局定义的地方。引脚映射、采样率、各种超时时间、枚举和结构体（比如 AudioChunk）都集中在这里。

nvs_mgr
配置持久化。WiFi 账号、灵敏度、宠物类型这些配置存到 NVS，token 是加密后存的，加密用的是 crypto_util 里的 AES。

led_mgr
状态指示灯。这个已经删了，GPIO18的灯不亮，LED 功能暂时不做。

power_mgr
电源管理，算是核心模块之一。管电池检测、240/80MHz 性能切换、省电档的间歇采样（1 秒听 3 秒睡）、三级休眠（静音 2 分钟进 LIGHT，10 分钟进 DEEP）、低电量分级保护。

sleep_mgr
夜间睡眠。0 点到 6 点自动进夜间模式，白天恢复正常，按键可以随时唤醒。

audio_mgr + es8311
音频底层。es8311 是编解码芯片的寄存器驱动，audio_mgr 负责 I2S 的采集和播放。

opus_encoder
OPUS 编码，默认 24kbps，960 采样一帧，也就是 60ms。

translate_mgr
翻译任务本体，也是问题最多、调试最久的一个。麦克风数据进来之后要过陷波滤波、AGC、静音门限判断，然后编码分片；另外它还管 TTS 下行播放，把服务器下发的 OPUS 解码后往喇叭写。

wifi_mgr
WiFi 连接和断线重连，还有 OTA 升级和网络白名单。

ble_provision
BLE 配网。手机 App 通过蓝牙把 WiFi 账号密码、宠物类型这些写进设备。

ws_client
WebSocket 通信。音频分片、定位数据上报、心跳（25s ping、8s pong 超时）、服务器命令分发都走这里。

wifi_location
定位。硬件没有 GPS，靠 WiFi 扫描加 BLE 做大致定位，还有居家省电逻辑（在家里定位间隔拉长到 30 秒）。

cache_mgr
断网缓存。音频最多缓存 25 块（约 10 秒），定位缓存 50 条，断网先存着，重连后补发。

ota_mgr
OTA 回滚，做了启动计数和分区切换。但实际上因为分区表是 huge_app 单分区，回滚用不了，真正的 OTA 是 wifi_mgr 里的 performOTA 直接更新固件。

lsm6ds3
6 轴 IMU 驱动。引导时自检，运行中读温度，夜间低功耗模式用来检测移动。

crypto_util
AES-128-CBC 加密加 CRC32。token 加密和音频分片校验用。

PetTranslator.ino（主文件）
把所有模块串起来：开机初始化、主循环、GPIO8 按键四档模式切换、服务器命令处理。

二、哪些模块测完了，哪些还没测

先说明一下，测试主要在两块板子上实测，Board 2 走原生 USB，配网相关的用 Board 2 更顺。大部分结果都记在 test_plan.md 里了，这里只按模块归一下类。

（一）已经测完的

基础启动（A1）：10 步引导完整，冷启动连续跑 50 分钟不重启，没有 FATAL。

nvs_mgr（J 项）：按键改配置重启后能保持，factory_reset 能恢复出厂，SN 和 AES 密钥会重新生成。中途修过一个严重 bug，getU8/getI32 的返回类型错写成 bool，导致所有数值型配置读回来不是 0 就是 1，修好之后持久化验证才算真正闭环。

power_mgr（F1/F2/F3/F4/F5/F7）：性能切换、间歇采样、三级休眠（LIGHT、DEEP、出声唤醒）、低电量分级、DEEP 每 180 秒周期唤醒，全都实测通过了。这中间修了不少 bug，比如间歇采样的 startIntermittentSampling 原来是死代码，翻译没运行时把"停止翻译"误判成"有声音"导致 CPU 被拉回 240MHz 等等。

sleep_mgr（D 项）：夜间进睡眠、按键唤醒、唤醒后 7 项恢复动作，都正常。

audio_mgr + es8311 + opus_encoder（G1/G2/E3）：麦克风能采到声音，OPUS 编码正常，功放开/关正确，喇叭能出声。这个模块折腾得最久：先是麦克风采集全零（es8311 初始化寄存器配错了，重写了一遍），然后播放无声（I2S 声道格式不对，改成 RIGHT_LEFT/STEREO），最后回声啸叫，干脆把产品形态改成"喇叭只播服务器 TTS"，移除了回声路径。

translate_mgr（E1/E2/E4/E5/E6）：翻译任务启停、静音检测、有声编码、静音停止编码、seq/total 语义，都闭环了。E5 调灵敏度（noise_gate）整套流程也验证完，门限调高能压住环境底噪，真实声音照样能录到。

wifi_mgr（C1/C2/C3）：自动连接、NTP 同步、断线重连。C3 修过一个 bug，原来 WiFi 重连任务失败一次就退出了，改成永久巡检之后复测通过。

ble_provision（B1/B4）：配网全流程通了，宠物类型 cat/dog/非法值都验证过，重启后能保持。

cache_mgr（E7 部分）：断网缓存补发链路实测过，补发时 retransmit=true 是对的，补发 25+ 块没问题。

lsm6ds3（A1）：引导通过，WHO_AM_I 是 0x6A。

压力测试（I 项）：连按 10 次按键、翻译 40 多次启停、长跑 50 分钟，都没崩，这个过得很干净。

（二）部分通过、或测出问题还没解决的

ble_provision B2（重置）：逻辑上能擦 WiFi 凭证，但实际配网成功之后 BLE 就不再广播了，导致 0x02 重置命令根本没有触发路径，属于设计缺陷，现在算是死代码。

B3（超时断开）：文档说 60 秒自动断开，实测连上 BLE 不提交凭证会一直挂着不断，跟文档对不上。

wifi_location（F6）：定位模块本身能扫描能计算，但"移动超过 30 米唤醒"依赖服务器解析坐标加设备绑定，一直没测成，后面要等服务器。

A2 电池充电：充电状态在满电临界会抖动；更麻烦的是拔 USB 直接掉电重启，这个基本确定是硬件问题（电池疑似没接系统负载，3.3V 全靠 USB VBUS 供），两块板都复现了，得硬件那边查。

（三）还没测的，基本都卡在服务器

E6/E7 的服务端核对：分片字段在设备端已经闭环验证，但服务器能不能正确解析、能不能区分实时数据和补发数据，要等服务端就绪。

H1/H2 定位上报：WiFi 定位每 3 秒扫描、loc_speed 字段是否正确，要服务器加设备绑定之后才能验。

F6 移动唤醒：要服务器 + 真实移动 30 米以上。

TTS 下行播放完整链路：要服务器下发 OPUS TTS 才能完整验证，目前只在自测固件里单独验证了编码解码到环形缓冲这段。

OTA 实际升级：回滚确定用不了（分区表限制，huge_app 单分区），OTA 升级功能在，但没对真实服务器验证过。

（四）几个还没闭环的坑

目前没测完的项目，绝大多数都是等服务器，设备端这边不算有阻塞。已知的限制主要是：WS 重连最多 10 次会停；MP3 降级编码没做（OPUS 跑得动，不作为阻塞）；GPS 相关需求全是 N/A，硬件根本没有 GPS。

三、目前测试中暴露的问题（还没解决的）

把现在还没解决的问题按来源归了一下类，一部分要硬件那边查，一部分是固件代码遗留的，还有一部分是必须等服务器才能继续的。

（一）硬件/板子层面的

1. 拔 USB 设备直接掉电重启。这个最严重。两块板子都复现了，现象一致：拔 USB 之后设备断电，插回去就是一次完整的重新上电。基本可以确定不是固件问题，是电源拓扑的问题——系统 3.3V 疑似只由 USB VBUS 供电，电池只接了 TP4065 的充电脚、没有接系统负载（或者电池接触不良）。要硬件那边确认原理图上 3.3V LDO 输入是不是并接了 VBUS 和 VBAT，然后拿万用表量一下拔 USB 后电池正极电压和系统 3.3V。

2. 充电状态在满电临界会抖动。4.55V/100% 满电时 [POWER] 的状态在 FULL/CHG/--- 之间不规则切换，这是 TP4065 充满截止和重充之间的边界抖动，PIN_CHRG_DET 读取不稳定。等电池放电到 95% 以下再复测。

3. 喇叭破音、音量偏小。这个是老问题，原版板子就有。问题汇总里记录的结论是：ES8311 的 DAC 寄存器 0x32 只能调到 0x08~0xA4 这个区间，超过 0xA5（也就是音量超过 65%）就会出现很大的杂音，D 类和 AB 类功放表现完全一致，所以功放没问题，问题在 ES8311 芯片本身，两端都不线性。另外播放满幅 0dBFS 数字信号时 ES8311 输出不会截幅。还有一个待验证的方向：需要示波器量一下 MCLK、SCLK、LRCK 的频率和幅度，重点看 SCLK 和 LRCK 的下降沿是否同步，不同步就会有杂音。

4. 不带电池喇叭带不动。调试的时候就发现，不装电池喇叭会断续破音，装上电池就好了而且音量会变大。这个和上面拔 USB 掉电可能是同一个根因（电池没接系统负载），需要硬件一起分析。

（二）固件代码层面遗留的

1. 按键中断首次启动偶发崩溃（ipc1 栈溢出）。烧录后第一次启动偶尔会 panic，重启第二次就正常，是 attachInterrupt 把 esp_intr_alloc 的深栈调用链派发到了只有 1KB 栈的 ipc1 任务上。已经改成直连 esp_intr_alloc 绕开 IPC 派发，编译通过了，但还没烧录反复复电确认，这个要尽快验证闭环。

2. BLE 0x02 重置命令是死代码。逻辑上能擦 WiFi 凭证，但实际产品形态下根本没有触发路径：有凭据时不进 BLE 配网，配网成功又马上断开 BLE 不再广播。要改成配网成功后延迟断开，或者加按键组合重置，否则这个功能等于没有。

3. BLE 超时断开和文档不符。文档说连上 60 秒不提交凭证就自动断开，实测一直挂着不断。代码里也确实没有空闲客户端超时断开的逻辑，只有配网成功后自动断开。

4. WS 重连超过 10 次会停。断线后 1 秒到 10 秒指数退避重连，最多 10 次，超过就停止自动重连，得等 WiFi 恢复或者手动触发。

5. OTA 回滚用不了。分区表是 huge_app 单分区，没有 OTA_0/OTA_1 槽位，ota_mgr 的回滚函数必然失败。实际 OTA 走的是直接更新整分区，能升级但不能回滚旧版本。

6. 地理围栏是半实现。setFence、setFenceEnabled、isFenceEnabled 和 NVS 参数都有，但 updateLocation 里没有越界检测的分支，不会切入围栏内的高频定位。

7. startDuplex 首帧 MIC 尖峰。每次开始采集后第一秒的 raw rms 会冲到很高（-21dBFS 左右）再回落，是启动瞬态。只有一帧，但可能被噪声门限误判成"有声音"而开一段 OPUS 编码。

8. E5 灵敏度调高的副作用。noise_gate 调高（sensitivity=100）能压住环境底噪，但副作用是 AGC 在输入变低时会把增益反向拉大，偶尔把安静信号放大越过节门，而且 sensitivity=100 会让三级休眠误判"一直有声音"、CPU 被拉回 240MHz，所以不能长期用，只能拿来验证。

9. TTS 解码有个待确认的边界。pushTtsOpus 单次调用只解码一帧（60ms），当前假设服务器每个 WS BIN 消息只装一帧 OPUS。如果服务器在单条消息里拼了多帧，会只解首帧丢后面的。这个等服务器联调时确认。

10. BLE JSON 长命令受客户端限制。BLE 默认 ATT MTU 23（载荷 20 字节），国产调试助手不协商 MTU 的话，33 字节的 JSON 命令会被截断。固件已经 setMTU(256) 了，但 MTU 由客户端决定，固件没法强制。兼容方案是 raw 的 06 xx 两字节 HEX 通道，不受 MTU 限制。

（三）必须等服务器才能继续的

F6 移动唤醒、H1/H2 定位上报、E6/E7 服务端核对、TTS 下行完整播放链路、OTA 对真实服务器验证。目前服务器还没就绪，没法测。

四、和服务器之间的通信协议

顺便把现在设备跟服务器怎么通信的整理了一下，方便以后对协议或者写服务器端参考。整体分两条路：一条是 WebSocket 长连接，音频、定位、状态这些主要数据都走它，服务器也能往下发控制命令；另一条是几个 HTTP 接口，用来激活设备、刷新 token，还有定位坐标解析。

（一）WebSocket 主通道

连接方式：设备拿到服务器地址后，用 WSS（端口 443，TLS 加密）连过去，连接路径会拼上身份参数，类似 /ws?sn=设备序列号&token=认证令牌，等于在 WebSocket 握手的阶段就把设备身份验了。

心跳保活：每隔 25 秒发一次 ping，服务器要回 pong；如果 8 秒内没收到 pong，就认为这条连接已经死了（半开连接），主动断开重连。重连用的是指数退避，1 秒、3 秒、5 秒、10 秒往上翻，最多试 10 次，超过就不自动重连了。

上行（设备发给服务器）：

1. 音频分片。这是最核心的一条。每一片先发一个 JSON 文本帧，再跟一个 OPUS 的二进制帧。二进制音频数据如果有加密密钥的话，会用 AES-128-CBC 加密再发。JSON 里带的字段有：sn、token、codec（固定 opus）、seq（段内序号）、total（段内总块数）、end（是不是段尾）、pet（宠物类型）、db（分贝）、bat（电量）、charge（充电状态）、rssi、ch（WiFi 信道）、fw（固件版本）、bound（是否已绑定）、ts（时间戳）、retransmit（是不是补发）、crc（校验）。有定位数据的时候还会追加 loc_type、loc_lat、loc_lng、loc_acc、loc_speed、loc_macs、loc_ts 这一串。

2. 独立定位上报。没有音频的时候单独报位置，格式是 {"type":"loc", ...}，带上经纬度、精度、速度、WiFi MAC 列表和电量信号这些。

3. 批量上传模式。服务器可以下发命令把上传模式切成"每 3 秒批量一次"。这种模式下设备先发一条 {"type":"batch","count":N} 的头部，然后把这 3 秒攒下的每一片按"meta JSON + 二进制"发出去。

4. 断网补发。断网期间缓存的数据，重连之后补发，走 {"type":"retransmit","seq":N,"retransmit":true,"crc":...} 加二进制帧，retransmit 标记是 true，服务器可以据此区分实时数据和补发数据。

下行（服务器发给设备）：

1. 控制命令。服务器下发的文本帧是 JSON，格式是 {"type":"命令名","data":"参数"}。目前支持的命令挺全的：set_sensitivity 灵敏度、set_volume 音量、enable_translate 开关节省翻译、enable_sleep 开关夜间睡眠、set_perf_mode 性能模式、set_pet_type 宠物类型、set_bitrate 编码码率、enable_location 开关定位、set_loc_interval 定位间隔、set_fence / clear_fence 电子围栏、set_home_wifi 家庭 WiFi、reboot 重启、factory_reset 恢复出厂、ota_update OTA 升级、bind_device / unbind_device 绑定解绑、set_record_mode 录音模式、set_upload_mode 上传模式、token_refresh 直接下发新 token、token_expired 通知 token 过期让设备走 HTTP 刷新。

2. TTS 音频。服务器下发的二进制帧就是 OPUS 的 TTS 语音，设备收到直接解码扔进播放缓冲往喇叭写。

（二）HTTP 接口

1. 设备激活。首次联网的时候 POST /api/device/activate，body 是 {"sn","fw_ver","mac"}，返回 200 时从响应里取 token 和 server_url，token 加密存进 NVS，server_url 更新进白名单，以后就用这个地址连 WebSocket。

2. token 刷新。服务器发 token_expired 命令的时候，设备走 POST /api/device/refresh，body 是 {"sn","token"}（旧 token），返回新 token 替换。这两个接口都是 WiFiClientSecure，但为了省证书校验的麻烦用的是 setInsecure()，等于不验服务器证书，安全性上以后可能要注意。

3. 定位解析。设备本身只负责扫描周围 WiFi AP 的 MAC 和信号强度，坐标是 POST 到服务器换的：body 是 {"sn","wifi_scan":[...]}，服务器返回 {"lat","lng","accuracy"}。没有服务器的话这步就永远不成功，经纬度全是 0，这也是前面说的 F6 移动唤醒测不了的原因。

另外提醒一点，目前协议里有两处对服务器的假设：一是假设服务器每个 WS 二进制消息只装一帧 OPUS（60ms），如果一条消息拼了多帧，设备只解首帧会丢后面的；二是蓝牙那条通道和 WebSocket 没关系，BLE 只管配网和少量配置，音频和定位这些主数据全走 WebSocket。对协议的时候可以拿这两条跟服务器那边对一下。

一句话总结：设备端功能基本齐了，本地能测的几乎都测完，剩下的都是服务端配套的活。目前最优先的是两件事：一是 ipc1 崩溃修复要烧录复电确认，二是拔 USB 掉电和喇叭破音这两个硬件问题要硬件那边出结论。
